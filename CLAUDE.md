# CLAUDE.md

Guidance for Claude Code when working in this repository.

## What this repo is

Infrastructure-as-code that builds a customized 64-bit Raspberry Pi OS (bookworm lite, from Raspberry Pi's "oldstable" downloads) SD-card image: the build "product" is the `.img` produced by Packer + Ansible. From Phase 3 on it also ships on-device application code — the `kestrel_pi` Python package (the plugin host, the web dashboard and the learning agent) under `builder/extra/files/`, with a `pytest` suite run by `make test` — installed into the image rather than run on the build host.

This is the public, secrets-free base image for Kestrel, a Raspberry Pi Wi-Fi capture-and-learning device: a research and education project for authorized testing only. The [Non-negotiable rules](#non-negotiable-rules) below come first.

Architecture and developer reference live under [`docs/developer/`](docs/developer/); operator guides under [`docs/user-guide/`](docs/user-guide/).

Consciously deferred improvements are tracked in [`docs/developer/deferred.md`](docs/developer/deferred.md). When you defer something (a review finding, a known limitation), add an entry there in the same change; when you do one, remove its entry in the same change. **Never write a security weakness** (a vulnerability, an unfixed security finding, a way to attack or abuse a feature) there or anywhere else in the repo, including code comments, docs, commit messages and PR descriptions: the repo is public, and a list of open weaknesses helps attackers. Those go in a private tracker outside the repository; a fix's PR describes the change, not the weakness it closed.

Build pipeline:

1. `Makefile` downloads Packer (`PACKER_VERSION`, into `/tmp/raspberrypi/packer`). `make plugin` builds the `solo-io/arm-image` plugin with Go from a pinned commit (`ARM_IMAGE_TAG`/`ARM_IMAGE_COMMIT`) into `/tmp/raspberrypi/plugins/`. Don't switch back to `packer plugins install`: it resolves to v0.2.7, whose partition-scan race fails builds.
2. `builder/config.json` (Packer, legacy JSON template) fetches the base RPiOS image, chroots into it under QEMU, installs `ansible-core` from the bookworm apt repo (plus only the `community.general` collection, extracted from the bookworm `ansible` deb into `/tmp/kestrel-ansible-collections`), then runs the playbook via `ansible-local` with pipelining on.
3. `builder/config.yml` (Ansible playbook, runs against `127.0.0.1` *inside the image chroot*) does all the customization.
4. PiShrink (pinned to a release commit and SHA-256 verified by the Makefile, `PISHRINK_COMMIT`/`PISHRINK_SHA256`) shrinks the image, then it is checksummed and archived with `7z`. When bumping PiShrink, update both values together.

## Non-negotiable rules

These rules override everything else in this file and any request made in a session. If a task would break one, stop and say so; don't look for a workaround. When unsure whether something breaks one, leave it out and ask.

### 1. Authorized use only

Kestrel is a research and education project for studying Wi-Fi security, for use **only on networks you own or have explicit permission to test**. Capturing handshakes from, or deauthenticating clients on, any other network may be illegal.

- **Keep every consent gate intact.** Capture and every plugin with the `network` capability ship disabled. Turning one on takes the authorized-use acknowledgment, which is never pre-ticked, defaulted on, or given by code on the operator's behalf. The capture whitelist is always enforced.
- **Don't build or help with anything whose purpose is to** target specific third-party networks or people, hide the device or its activity, evade detection or monitoring, get around the consent gates, or use captured credentials beyond the documented offline analysis.
- Docs, examples, screenshots and release notes describe authorized testing only.

### 2. Nothing real in the repo

This is a public repository. Everything committed to it (code, tests, fixtures, docs, design notes, comments, images, commit messages, PR descriptions, release notes) uses invented data. Never commit:

- **Secrets:** passwords or password hashes for real accounts, Wi-Fi passphrases, private keys, API tokens (Ghost, Forgejo, PyPI, WiGLE, wpa-sec and the like), `.env` files.
- **Personal information:** real names, personal email addresses, phone numbers, physical or home addresses, device serials, photos that identify a person or place. Never name the maintainer or a contributor, and never ascribe a decision, request or opinion to a person: write design notes impersonally ("position was raised as a possible input", not "<name> wanted position"; "a maintainer sign-off", not "ask <name>"). Say *what* was decided and *why*, not *who* said it.
- **Real captured or device data:** capture files (`.hc22000`, `.pcap`/`.pcapng` and the like), real SSIDs, BSSIDs or MAC addresses, real GPS positions or tracks, diagnostics bundles (the `scripts/pull-*.sh` output), device logs, a real device's `config.toml` or state files, screenshots of a real device, models trained on real captures, WiGLE or wpa-sec results.

Use these placeholders instead:

| Kind | Use |
| --- | --- |
| Domains, emails | `example.com`/`.net`/`.org`, `*.example`, `user@example.com` (RFC 2606) |
| IP addresses | `192.0.2.0/24`, `198.51.100.0/24`, `203.0.113.0/24` (RFC 5737), or the documented device subnets (`default.conf`) |
| MAC addresses | `00:00:5E:00:53:xx` (RFC 7042) for new code; the existing tests' `AA:BB:CC:xx:xx:xx` style is also accepted |
| SSIDs | `My Network`, `Cafe Guest`, `Library WiFi` |
| GPS | generic coordinates, such as `12.34567, -45.67890` |
| Screenshots | the demo fixture (`tools/ghost-guide/fixture.py`) or other invented data |

The only real identifiers allowed are the functional public project identity and upstream sources: the `aluminum-ice` handle and the `git.3ntropy.io` forge (clone URLs, release links, the `updates` plugin's default repo and host), the public guide page on `www.3ntropy.io` only where the publisher needs it (`tools/ghost-guide/guide.toml`) or a doc names that page, upstream source URLs, the documented default `pi`/`raspberry` hash, `pi@kestrel.local`, and the role-based reporting alias `security@3ntropy.io` in `SECURITY.md`. Nothing else, including in examples: an example uses a placeholder even when the real value would be clearer.

Where real values live instead:

- `system.account.pi` holds the documented DEFAULT hash (`pi` / `raspberry`). A real one comes from the `MY_PI_PASSWORD_HASH` env var at build time.
- `system.network` is empty and `builder/extra/deployments/` ships empty. Real Wi-Fi networks are added at build time (env var or an uncommitted edit) or on the device.
- Tokens and keys live in the environment or in device config, never in a file in the repo.

Commits use the project identity `aluminum-ice <aluminum-ice@noreply.git.3ntropy.io>`, set in the repo-local git config; check `git config user.email` before committing. (The PR attribution line the harness adds to a PR body is not repo content and is exempt.)

**Enforcement.** `make lint` (and so the Lint workflow) runs `tools/real-data-check/`, which fails on MAC addresses and emails outside the placeholders above, private keys, token-shaped strings, password hashes other than the documented default, hashcat capture lines with non-placeholder MACs, and capture, GPS-track, model, key or diagnostics-bundle files. A Claude Code `PreToolUse` hook (`.claude/hooks/real-data-check.sh`) runs the same check before any `git commit` and blocks it on findings, and `.gitignore` keeps those file types out of `git add`. None of these can recognise a real SSID, a real coordinate or a screenshot of a real device; those are on you. Never weaken the check or the hook to get a commit through. If the check flags a genuine placeholder, add it to the check's allowlist in the same change and say why.

**If you find real data:** stop, don't commit it, and tell the maintainer. If it is already pushed, treat any secret as leaked: it has to be revoked and replaced, because rewriting history doesn't unpublish it. Raise whether history needs rewriting; never rewrite history on your own. `.claude/settings.json` also blocks reading `.env` and `*.key` files as a safety net; don't work around it.

## Building and validating

A full build needs root, `qemu-user-static`, loop devices, `parted`/`e2fsprogs` for PiShrink, ~15 GB of disk and a long run time. **Do not try a full image build in a Claude Code session** (cloud or local) unless the user asks for one. Real builds run through the Forgejo Actions "Release" workflow.

```bash
# Full build (needs root): produces kestrel-<version>.{img,sha256,7z,7z.sha256}
sudo make image
MY_VERSION=1.2.3 sudo make image   # override version from _version.py
make clean
```

Static checks (no image build) are run by `make lint`, using the tools pinned in `requirements-lint.txt`:

```bash
pip install -r requirements-lint.txt   # done automatically in cloud sessions by .claude/hooks/session-start.sh
make lint
```

`make lint` runs `ansible-playbook --syntax-check` on the playbook, `yamllint` (config: `.yamllint`) on all YAML, `shellcheck --severity=error` on all `*.sh`, and the real-data check (`tools/real-data-check/`, see [Nothing real in the repo](#2-nothing-real-in-the-repo)). The same target runs in the **Lint** workflow (`.forgejo/workflows/lint.yml`) on every push and PR. Run it before committing. A passing lint does not mean the image builds; say so instead of claiming a build was validated.

The on-device `kestrel_pi` package also has unit tests: `make test` runs them (venv `pytest`, needs `flask`/`requests` plus `numpy` for the agent spec import, `pillow` for the e-ink renderer and `cryptography` for the dashboard certificate; `torch`/SB3 are stubbed, not required), then the real-data check's own tests; `make lint` only byte-compiles the package. The **Test** workflow (`.forgejo/workflows/test.yml`) runs `make test` on every push and PR, alongside the Lint workflow.

## Verifying a beta

Every beta (`X.Y.Z-beta.N`) is verified on a device before the stable release, in three steps:

1. **Checklist issue.** Once the Release run has published the beta, open an issue titled "On-device checklist for X.Y.Z-beta.N". Open it with a line saying the issue is public, so results, logs and screenshots use placeholders and never a key or passphrase. Then list one numbered checkbox (`3.5`, ...) per thing to verify, grouped by the change behind it and derived from the diff since the release the beta is built against. Tag every item the script can't judge **🖐 by hand** when you write it (how a page looks, a hidden prompt, a real upload, a fresh flash), and keep only the stable release (or the next beta) as the closing step.
2. **Check script.** Update `tools/beta-check/` for the beta so that every item the device can show is a `CHECK <item number>` in `beta-check-device.sh`, keeping every rule in `tools/beta-check/README.md`. Those rules are part of this file's non-negotiable rules. In short:
   - **Publishable:** the scripts hold no secrets, personal information, hosts, IPs, URLs, account names or passwords, so they are safe to post in this public repo and its issues.
   - **Read-only:** they never touch the management link (`nmcli`, `bluetoothctl`, `ip`, `rfkill`, `iw`) and never start, stop or restart a service. They write `config.toml` only as a throwaway copy, checksummed to prove the real file is unchanged.
   - **Nothing real leaves:** they read no capture content, and everything is redacted on the device before it leaves.
   - **Lands in a PR:** the update goes in a PR like any change; the scripts aren't shipped, so it doesn't affect the release kind.
   - **Checked before attaching:** `make lint`, the off-device harness and redactor checks from the README, then `python3 tools/beta-check/attach.py <issue> <version>`. That zips the scripts as `beta-check-<version>.zip` (the forge rejects `.sh`) and attaches them to the issue; post a comment naming it and the command to run. The first run on a device is the scripts' first real test, so say so.
3. **Review.** The maintainer runs the script and hands over the report, `kestrel-beta-check-<time>.txt`, privately (from a folder outside the repo). It is never attached to the public issue. Read it for anything real before quoting from it; if it holds real data, stop, quote nothing, and say so. Then edit the issue from its current text (the maintainer ticks boxes too; never overwrite their edits):
   - tick only an item the report shows was checked and passed, and add **✅ script**;
   - leave failures, `INFO`, `SKIP` and anything inconclusive unticked, and report them to the maintainer in the session rather than on the issue;
   - add **🖐 by hand** to every item that is left for the maintainer.

   A fix for a failure goes into the next beta, not the stable release.

## Conventions and gotchas

- **Ansible version is pinned by the OS.** The playbook runs with the `ansible-core` package from the bookworm repos (2.14) *inside the image*, not whatever is on the build host or in `requirements-lint.txt`. Don't use modules or options newer than 2.14. Note `command` no longer accepts `args: warn:`. Only `community.general` is available beyond the builtins (see `builder/config.json`); a module from any other collection needs its collection extracted there too. **Build speed:** every module run starts Python under QEMU (~1.5 s, two per file for `copy`), so install multi-file groups with one `install`/`cp` shell task, not a `copy` loop or a directory `copy`; the big `pip install` runs `async` and is collected by "wait for the pip packages" before `kestrel_pi` installs, so tasks in between must not touch the venv.
- **Bookworm specifics:** system `pip install` is blocked (PEP 668), so Python packages go only into `/home/pi/.venv`, after `pip.bootstrap`. Wi-Fi uses NetworkManager profiles, not `wpa_supplicant.conf`. SSH is enabled with `raspi-config nonint do_ssh`. The apt upgrade and Ethernet-over-USB tasks are commented out on purpose (see the comments in `builder/config.yml`). The boot (FAT) partition is at `/boot/firmware`, on the device and in the build chroot (`image_mounts` in `builder/config.json` overrides the arm-image plugin's `/boot` default for RPiOS). Reference it only through `system.boot_dir`; `/boot/config.txt` in the rootfs is a "this file has moved" stub. The playbook fails early if `system.boot_dir` doesn't hold `config.txt`/`cmdline.txt`. Boot options go in one `[all]` block in `config.txt`.
- **Don't let apt remove stock Raspberry Pi packages.** The legacy `libraspberrypi-bin`/`libraspberrypi0` conflict with `raspi-utils` (which provides `vcgencmd`); installing them made apt remove `raspi-config`, `raspberrypi-sys-mods` (the first-boot resize), `pi-bluetooth`, `rpi-eeprom` and `userconf-pi`. `packages.general.protected` lists packages the build checks are still installed right after the apt install; extend it rather than weakening it.
- **Prefer editing `vars:`.** To add or remove apt packages, pip packages, boot options, kernel modules or services, edit the lists under `vars:` in `builder/config.yml` instead of adding new tasks. Keep the README package table in sync when changing `pip.local.install`.
- **Capture is runtime config, not Ansible vars.** The AngryOxide capture service reads `/etc/kestrel/config.toml` (shipped from `builder/extra/files/config.toml`, parsed by the `config-get` Python helper via stdlib `tomllib`), separate from the network plumbing in `/etc/default/kestrel`. The capture scripts (`capture-launch`, `capture-collect`, `config-get`) and systemd units live under `builder/extra/files/`, installed by the "kestrel capture" block in the playbook. Capture ships **off**; only `kestrel capture enable` turns it on, after an authorized-use acknowledgment. The versioned surface the agent and plugins consume is `docs/developer/capture-interface.md` (`contract_version`).
- **Connectivity:** scripts, the `kestrel` config tool, the `default.conf` and the systemd units live in `builder/extra/files/` and install to `/usr/local/{bin,lib}/kestrel`, `/etc/default/kestrel` and `/etc/systemd/system/`. Shell files keep their `.sh`/`.py` suffix in the repo (so `make lint` shellchecks them) and install without it. Scripts source `common.sh` and read `/etc/default/kestrel`; keep them POSIX-ish bash that passes `shellcheck --severity=error`. Bluetooth pairing is Just Works gated by a time-limited onboarding window, not a PIN.
- **Plugins:** the plugin-host daemon is the `kestrel_pi` package under `builder/extra/files/kestrel_pi/` (with `pyproject.toml` and `tests/`), pip-installed into the pi venv from its in-image source by the "kestrel plugins" playbook block; its entry point is `kestrel-daemon` and the unit (`kestrel-daemon.service`) ships **enabled** but inert without enabled plugins. Seven of the fourteen reference plugins (memtemp, session-stats, gps, wpa-sec, wigle, `backup` — an opt-in rsync/scp-over-SSH mirror of the capture store to a remote host; `kestrel backup setup` installs the pi key via `ssh-copy-id`, so the remote password is never stored — and `ups-hat` — Waveshare UPS HAT battery readout over the INA219 I2C fuel gauge, which confirms the HAT is present by round-tripping a register before acting, and cleanly auto-shuts-down at/below a configurable `shutdown_percent` while on battery via the root power helper) live in `builder/extra/files/plugins/` (installed to `/usr/local/lib/kestrel/plugins/`, operator plugins override from `/etc/kestrel/plugins/`); all ship disabled in `config.toml` under `[daemon]`/`[web]`/`[plugins.*]` (`builder/extra/files/plugins/` also holds the `eink`, `updates` and `remote-train` plugins described below, and `downloads`, `map`, `notify` and `hat-buttons`, so fourteen plugins ship in all). `downloads` is local only (`capture-read` + `web`, no ack): it zips the store's top-level `*.hc22000` files (all, or changed since the last zip via `seen.json`; optionally with their `.gps.json` sidecars) or serves them as one de-duplicated `.hc22000`, never `cracked/` or `archive/`, and only to a request with `web_authed` that arrived over HTTPS (`request.is_secure`) or loopback. Files are read with `O_NOFOLLOW|O_NONBLOCK` after an `lstat` regular-file check; the zip is built in `~pi/.local/state/kestrel-downloads/` and deleted after it streams. `map` is local only (`capture-read` + `location` + `web`, no ack): a server-rendered SVG of every location from the core `GeoStore.locations()` (recorded pin vs estimated `~` ring, grid clustering with zoom-by-link `?bbox=`, graticule, scale bar, north arrow; no map tiles, so no tile server learns where you captured), drawn twice (landscape and a phone-shaped portrait) and swapped by the shared stylesheet's `.wide-only`/`.narrow-only`; it needs `web_authed` and reads `[web] show_locations` live from `config.toml`. `notify` (`network` + `capture-read` + `ui` + `web`, so the ack) sends alerts to ntfy (default; a long random topic is generated and kept `0600` when `ntfy_topic` is empty) or Telegram: a handshake digest (counts only unless `include_names`), battery low / on battery (from `UIState.battery`), an update (the `updates` state file) and capture stopping while `[capture] enabled` (two updates down). Messages are built from typed fields only; a worker thread keeps an offline queue (50, persisted) with `max_per_hour`, `quiet_hours` (urgent alerts bypass) and backoff. Requests go through `httpsafe`, and transport errors are reduced to their type so a Telegram token in the URL never reaches a log or the card. It only sends; there are no commands back. `hat-buttons` (`ui` only, no ack) reads the 2.7" HAT's KEY1-KEY4 with gpiozero (lazy-imported in `_make_button`; `pins` default BCM 5,6,13,19, from a community source and to be confirmed on hardware): KEY1 short toggles an info screen, a long KEY2 stops capture (never starts it), a long KEY3/KEY4 arms a reboot/shutdown that a second press within 5 s confirms. Callbacks only queue events; a worker acts through `context.apply` (the same validated `capture`/`power` targets as the dashboard). It provides a `buttons` service (`seq`, `screen`, `prompt`) that `eink` consumes optionally: the info screen replaces the face, a prompt takes the voice slot, and the render loop wakes within a second when `seq` changes. The `plugins` subcommand of the config tool drives enable/disable via the `plugins-ctl` helper, run as `/usr/bin/python3 -I` like the socket helpers (never the pi venv: `plugins-ctl` reads declarations statically in every subcommand and imports neither plugin code nor `kestrel_pi`); enabling a plugin with the `network` capability takes the same authorized-use ack as capture. The web page's plugin controls (on whenever `[web] auth` is not `none`) never write config.toml from the daemon: they go through the root `plugins-ctl apply` helper behind `kestrel-plugins-apply.socket`, which reads plugin declarations with `ast` and must never import plugin code (it runs as root). `[web] auth` defaults to `system`: the page logs in with the device account (same credential as SSH), verified live against `/etc/shadow` by the root `plugins-ctl checkauth` helper behind `kestrel-web-auth.socket` (the daemon is `pi` and can't read shadow); no web password is stored, so it can't drift from the SSH login. Off the device the dashboard is **HTTPS** (`[web] tls`, default `on`, and `tls_port` 8443 are code defaults, not shipped config): `kestrel_pi/webtls.py` makes a self-signed P-256 certificate as `pi` in `~pi/.local/state/kestrel-web/` (an 820-day validity span, under the 825 days Apple and Chromium-on-macOS accept; reissued near expiry or when a span is over that limit; fingerprint via `kestrel web fingerprint` and, briefly after start-up, the e-ink panel), and `[web] port` on a management link only redirects (307) to HTTPS. Loopback stays plain HTTP with Basic, so on-device tools and the beta check keep working. Browsers sign in once on `/login` and carry a signed, stateless `kestrel_session` cookie (`HttpOnly`, `Secure`, `SameSite=Strict`; keyed by `session.key`, so daemon restarts don't sign anyone out; `kestrel web logout-all` rotates it), with a login-CSRF token and a per-address backoff; Basic credentials are accepted only over HTTPS or loopback (or anywhere while `tls` is off). The HTTPS handshake is deferred to the connection thread so a stalled client can't hold up the accept loop. `spwd`/`crypt` are imported lazily in `plugins-ctl` (removed in Python 3.13, present on the 3.11 image) so the module still loads under a newer host Python; keep them lazy. Keep the API modelled on legacy pwnagotchi (`Plugin` base class, the familiar `on_*` hook names; it is not drop-in compatible, since several hooks take a typed event and `self.context` instead of pwnagotchi's `agent` object), but plugin declarations (`__options__`, `__capabilities__`, `__provides__`, ...) must be **plain literals on a direct `Plugin` subclass**: root reads them with `ast` (`kestrel_pi/declarations.py`, mirrored in `plugins-ctl` with a drift test) and the loader refuses a plugin that reader can't read, so root and the daemon see the same plugins; the legacy `@plugins.on` decorator style is not supported. Root runs Python only as `python3 -I` (common.sh resets `PATH` for root) and the venv's Python only via `run_as_pi`; `tests/test_root_python.py` enforces it. Honor the hook-API version (`HOOK_API_VERSION` in `kestrel_pi/__init__.py`): bump it on any breaking hook-signature change (e.g. the Phase 5 `on_ui_*` args). A plugin declares **up to two** Plugins-page row buttons in `__actions__` (varied live via `webhook_actions()`), each routing to its own `on_webhook` — a `get` navigates to a page the plugin renders, a `post` performs an action; this replaced the old bespoke per-plugin button routes and is additive, so `HOOK_API_VERSION` stays `1`. The functionality lives in the plugin via the context: `context.apply(change)` reaches the same root `plugins-ctl apply` helper (so a POST button grants no new privilege — the helper still validates every target), and `context.page(title, body)`/`context.redirect(message)` are the flask-free `on_webhook` result markers (core wraps a page in the shared shell or redirects to the Plugins page with a banner, gates a POST on auth+CSRF before dispatch, and a plugin never imports `web.py`); the shared `applyclient.py` holds the apply client so both the web layer and plugins use it without importing the web server. A plugin that sends a credential (wpa-sec, wigle) goes through `kestrel_pi/httpsafe.py`: `https://` endpoints only, no redirects (`requests` re-sends a `cookies=` value to a redirect target), and size-capped reads. Tests run with `make test` (venv `pytest`, needs flask/requests); `make lint` only byte-compiles the package. Keep the target Python at 3.11 (ansible-core 2.14-era image), so no 3.12+ syntax.
- **Device web UI:** grows the status page into the device dashboard and control surface. Plugins contribute to the dashboard as **data** (typed `on_ui_*` readout cards from the shared, per-plugin UI element model in `ui.py` — `StubUI.for_plugin()` namespaces elements; `status()` exposes a grouped `widgets` map) **or own a page** (`on_webhook`), never by injecting markup into the dashboard shell (core escapes all widget values). The element shape widened to `{label, value, kind}` (kinds text/number/percent/gauge) **source-compatibly**, so `HOOK_API_VERSION` stays `1` — the bump is reserved for Phase 5's real `on_ui_*` args. **Capture on/off and the authorized-use ack are drivable from the page** through the *same* root `plugins-ctl apply` socket (a `{"target":"capture",...}` change), which shells out to the shipped CLI (`capture enable --yes` / `capture disable`) so adapter detection, the config write and the service enable match the terminal; the ack is explicit, never pre-ticked, recorded in the shared `capture-ack` file. Controls need `[web] auth` on (read-only otherwise); a capture toggle does **not** restart the daemon (capture state is read live via `systemctl is-active`). The web and e-ink views share the state model but **not** layout (the web may drop the mascot).
- **Learning agent:** an optional RL policy that picks the capture scan posture each decision window, in its own `kestrel-agent.service` (runs as `pi`, `NoNewPrivileges`; torch/SB3 lazy-imported only in this process so an OOM can't take down the always-on daemon). Opt-in and gated by capture — the process exits 0 unless `[capture] enabled`, and the `[agent] enabled` gate is the systemd enable state plus the launcher's `agent_active()`. It drives capture **only** through the Phase 2 launch-time seam: the controller writes `scan-override.json` (only when its plan changes; the launcher relaunches only on a content change, since every relaunch restarts the scan) for the capture launcher to read; it never starts AngryOxide and never edits `config.toml`. The fixed env contract is `kestrel_pi/agent/spec.py` — `SPEC_VERSION` (recorded in the model sidecar; distinct from the capture `contract_version` and `HOOK_API_VERSION`; bump only on an observation/action shape change), a flattened `Discrete(32)` action (4 postures × 4 dwells × 2 transmit modes) and a fixed 389-wide `Box` observation. `[agent] algorithm` selects the SB3/sb3-contrib class (RecurrentPPO default; PPO/DQN/QR-DQN swap with no code change because the spaces are a plain `Discrete`/`Box`), and the scripted sweep (`policy = baseline`) is always the fallback and the scoring reference. Models are loaded **as weights only** (`policies._load_weights`: a fresh model for the spec spaces, then `set_parameters`), never with SB3's `cls.load`, which restores pickled objects from the file and so could run code from a model that came off a training host or the boot partition. SSH to the backup and training hosts requires the key recorded at `setup` (`StrictHostKeyChecking=yes`), never `accept-new`. Inference is on-device; training is offline and **state-conditioned** (`agent/train.py`), with a RAM/thermal-gated on-device fine-tune (needs ~4 GB RAM, so never on a Zero 2 W), a boot-partition model import (`agent-provision`), and the `remote-train` plugin (`docs/developer/remote-training.md`) running the identical trainer on a desktop over SSH. The daemon renders the agent's `status.json` on a dedicated `/agent` page and never imports the agent package, so torch stays out of the always-on daemon. Keep the target Python at 3.11.
- **E-ink face:** the `eink` plugin draws the classic animated "tamagotchi" face on a Waveshare 2.7" e-Paper HAT (264×176 mono), driven by live state. It is a normal Phase 3 daemon plugin (`builder/extra/files/plugins/eink.py`), ships **disabled**, local-only (no `network` capability, so no authorized-use ack), and degrades cleanly with **no HAT** (renders only to the web mirror). The Waveshare driver is **vendored** in the package (`kestrel_pi/vendor/waveshare_epd/`, MIT header kept, V1 `epd2in7.py` + V2 `epd2in7_V2.py`, `variant=auto` probes); the plugin **lazy-imports the driver and PIL inside methods**, never at module top, so importing it off a Pi (tests, build host) touches no SPI/GPIO. Phase 5 locks the `on_ui_*` contract: `on_ui_update(self, ui, state)` gains a read-only `UIState` snapshot (`ui.py`), bumping `HOOK_API_VERSION` 1→2 (all nine other plugins updated to the 2-arg signature). The daemon exposes an `agent` readout service and `ups-hat` a `battery` provider (like gps `position`); the face consumes all three as `__optional_requires__` and a `MoodInputs`→`decide_mood` **priority ladder** (fault→power→milestone→handshake→agent-posture→idle→base; "the face never lies" — `smart` only under a learned policy). The panel shows a top icon strip (BT PAN + Wi-Fi link glyphs from `UIState.paths`, a GPS satellite + signal bars gated on `services.has("position")` — outlined searching / solid locked, bars from the fix's strongest-sat C/N0 — and a battery gauge with percent from `battery`), the mascot face offset to the left (the face *is* the mood) with a mood-matched **voice** phrase beside it (per-mood `_VOICES`, rotated on mood change so no redraw just to reword, operator-overridable via `[plugins.eink.voices]`; for `show_fingerprint_minutes` (default 10) after start-up the voice slot instead shows the start of the dashboard's HTTPS fingerprint (`webtls.fingerprint()`, through an overridable `_fingerprint_lines()` the ghost-guide fixture turns off)), a compact symbol-led status row (chip glyph + agent `off`/`baseline`/`learned`, antenna glyph + capture state), an info row (`UP` uptime from `UIState.uptime`, and while capturing `CH` the channel plan — `format_scan_channel()` reads the agent's `scan-override.json` when it drives, else `[capture.scan]`; it is the plan, not a live tune), an address row (each management link's IPv4 behind its BT/Wi-Fi glyph, `show_ip` default on; looked up with a `SIOCGIFADDR` ioctl through the overridable `_addresses()`, which the ghost-guide fixture replaces with a placeholder so a screenshot never shows a real address), and a bottom counter row — the plain-English trio "N handshakes from M access points across K networks": `PWND` captured handshakes `UIState.capture_total` with `capture_session` in parens (e.g. `240 (30)`), then `AP` distinct radios `UIState.aps_total` and `NET` distinct networks `UIState.networks_total`, both lifetime (AP/NET are lifetime-only so all three fit one row left of the brand mark) — and the Kestrel mark once in the lower-right whose pose carries motion (stoop when moving). Motion is estimated from GPS speed (successive fixes, haversine) as **parked / walking / driving** (thresholds `_PARK_MS`/`_WALK_MS`/`_DRIVE_MS` with a deadband + sustain), shown as a person/car glyph in the top strip only while moving (parked shows no top glyph — the Kestrel's hover pose denotes stopped) and on the dashboard Motion card. The `gps` plugin's `position` service return is enriched additively (adds `fix`/`sats`/`cn0`/`strong`) so the face reads signal without owning a reader; the three capture counts come from the daemon's single `CaptureInterface.capture_counts()` (`handshakes`/`access_points`/`networks`), the same call the dashboard navcard reads, so the face and the page can't disagree — "access points" is distinct radios (BSSIDs), "networks" distinct names (ESSIDs). The session handshake delta (`capture_session`) is tracked live. The **live web mirror** (`__actions__` "View" GET → `on_webhook` serving a PNG of the exact frame) reuses the Phase 3 plugin-actions API; it cannot drift (single in-memory last-frame store + `_frame_seq` ETag, reloads at the same `refresh_seconds`). The Kestrel mark is drawn from its SVG path in code (no binary asset). **Gotcha:** a plugin module is loaded by the loader **without** being registered in `sys.modules`, so a module-level `@dataclass` under `from __future__ import annotations` crashes at load (dataclass's `KW_ONLY` scan does `sys.modules[cls.__module__]`) — keep plugin-module dataclasses off the future-annotations import. **Build impact: reflash-class** — it adds apt packages (`python3-spidev`, `python3-gpiozero`, `fonts-dejavu-core`), which the app-layer update engine does not install. Target Python 3.11; `make test` covers the mood ladder, the no-HAT path and the mirror.
- **In-field updates** (`docs/developer/updates-setup.md`): the opt-in `updates` plugin alerts on a newer GitHub release; the dashboard/CLI then apply an **app-layer** update in place (no reflash) via the root `plugins-ctl apply` `{"target":"update"}` socket → the shipped CLI's `update apply`, which clones the release and `exec`s the clone's `builder/extra/files/update-apply.py` engine (running from the clone is what makes overwriting the installed CLI/`plugins-ctl`/package safe). The engine reinstalls everything the playbook installs **from under `builder/extra/files`** (the `kestrel_pi` venv package, `plugins/*.py`, the systemd units, the journald drop-in, and the fixed `LIB_SCRIPTS` list of lib scripts + the CLI) and deliberately **skips operator config** (`config.toml`, `/etc/default/kestrel`) — new config keys fall back to code defaults. The build stamps `/etc/kestrel/version` (`master` for a no-`MY_VERSION` build = dev, never offered updates). Each release carries an `update-manifest.json` (`kind: app-layer|reflash`); no manifest ⇒ treated as reflash.
  - **Root trusts only root-owned inputs.** `kestrel update apply` takes the host/repo/token only from `config.toml`, where they are `root_only` options (set only from the terminal, never through the apply socket; see "Anything `pi` can write is untrusted input to root" below) and re-verifies the release as root (`update-apply --verify`: published, non-draft, newer, on the channel, app-layer, manifest-pinned commit, no skipped reflash); the pi-written `state.json` is a hint for *which* release, never trusted. Root never writes into the pi-owned `/var/lib/kestrel/update/` (symlink redirection): the check trigger is only created fresh with `O_EXCL|O_NOFOLLOW` and never chowned, and the engine's run status, lock, in-progress marker, install list and backups live in root-owned `/var/lib/kestrel/update-run/`. The engine installs each file atomically, snapshots/restores the package as pi, rolls back if the daemon doesn't stay up after the restart, and `kestrel-update-recover.service` rolls back an interrupted update at boot. The web passes the confirmed tag through `plugins-ctl` (`--expect`); keep those properties when changing this path.
  - **Beta channel:** `release_version` must be `X.Y.Z` (stable) or `X.Y.Z-beta.N` (beta; the workflow refuses anything else). The workflow derives `PRERELEASE` from the suffix: a beta is published as a Forgejo pre-release, skips PyPI, and its manifest/notes are built against the highest release below it, while a stable release's are built against the previous *stable* one (so betas can't hide a build change from stable devices). The plugin's `beta` option (default off) opts a device in; versions compare by SemVer precedence (`version_key`), and the reflash-gap scan includes betas only when the offered release is a beta. Only `-beta.N` is supported (no rc/alpha).
  - **Setting `update_kind` before a Release run (the maintainer's call Claude makes for them):** the Release workflow's `update_kind` input defaults to `auto`, which marks a release **reflash** when the diff since the previous release touches `builder/config.json`, `builder/config.yml`, `Makefile` or `.forgejo/workflows/` (or the old `.github/workflows/`) — so a `config.yml` edit trips reflash by default even when it is harmless. **A `config.yml` change is safe to set `update_kind=app-layer` only when every hunk is one the in-place engine already carries into a running device**, namely: a `copy`/`template` (or `install`/`cp` shell) task whose source is a file under `builder/extra/files` **and** whose destination is one the engine already writes — a `plugins/*.py` plugin, a `systemd/*.{service,socket,timer}` unit, the journald drop-in, the venv package, or the CLI; plus pure comment/formatting/`boards:`-reference edits. **It is reflash (leave `auto`, or force `reflash`) whenever a hunk touches anything the engine does not apply:** apt packages (`packages.*`, incl. `protected`), pip packages (`pip.*`), boot options/`config.txt`/`cmdline`, kernel modules, the system account/hostname/network, the base image or partition size, **a brand-new installed *lib script*** (the engine's `LIB_SCRIPTS` is a fixed list — add the new script there in the same change, or it won't install on an app-layer update), a new install **destination** outside the covered set, or any shipped-default change to `config.toml`/`default.conf` (the engine skips operator config, so the new default never lands on an updated device). When unsure, leave it reflash — app-layer is the exception you justify per-hunk, never the default.
- **Web pages follow `docs/developer/web-ui-conventions.md`.** Every built-in web page (the daemon status/manage pages, the Phase 3.5 dashboard, plugin `on_webhook` views, and the Phase 5 e-ink plugin's rendering) is server-rendered in Python and dependency-free: no JS framework/SPA/component library (no React, no antd) and no client-side build step, because the pipeline has no JS toolchain and nothing under `builder/extra/` may be generated. Make it look modern with CSS, not a library. Pages are mobile-first and responsive (viewport meta, fluid container, touch targets, wide tables reflow into cards via `data-label` + hidden `thead`), dark-mode aware via CSS variables under `prefers-color-scheme`, and status is never shown by colour alone. One shared inline stylesheet (`_STATUS_CSS`) via `_page()`; assemble CSS/JS by concatenation (literal `{}` breaks `str.format`); escape via `_esc()`/`_js()`. Keep the security rules: management-link bind only, HTTPS and the sign-in session off the device, `[web] auth`, CSRF on writes, the frame/cache/referrer/`nosniff` headers, never echo a secret. `_page()` also appends a **Documentation** footer linking `/guide`, the on-device operator user guide: its content is `GUIDE_MD` (Markdown) in `kestrel_pi/userguide.py`, rendered by the small built-in `_render_markdown()` in `web.py`. Keep `GUIDE_MD` current when a feature changes how an operator configures or uses the device (update it in the same change), and keep it free of personal information — it ships in the image. The public Ghost user-guide page is generated from the latest stable release's `GUIDE_MD` by `tools/ghost-guide/` (never edited in Ghost): blog-only text and screenshot placement live in `tools/ghost-guide/guide.toml`, and its demo data must stay fictional.
- **Anything `pi` can write is untrusted input to root.** That includes `config.toml` changes made through the apply socket (any `pi` process can reach it, not only the web page), the capture store, the venv and `/var/lib/kestrel/update/`. So:
  - A plugin option a root process acts on is declared `"root_only": True`. The socket refuses it and the web page shows it read-only; only `sudo kestrel plugins ... --set` (`plugins-ctl set`) changes it.
  - A `CONFIG_SETTABLE` path or file name carries a `pattern` or `under` constraint (mirrored in `config_catalog.py`; the drift test keeps them equal), and the code that uses it re-checks it.
  - File work inside a `pi`-owned directory runs as `pi` (`run_as_pi`, or `setpriv` for a long-running process), never as root, so a planted symlink can't redirect it. AngryOxide (root) writes its raw output to the root-owned `/var/lib/kestrel/capture-run/` (`root:pi 0750`, set by the launcher), the collector runs as `pi`, and the store's archive/clear steps run as `pi` through `kestrel capture _store`. The one exception is `capture-collect --adopt-store pi`, which the launcher runs as root to hand files an older (root) collector left in the store to `pi`: it works only on descriptors opened relative to the parent with `O_NOFOLLOW`, re-checks each through its descriptor, `fchown`s that descriptor, and touches only single-link regular files and folders owned by root on the store's filesystem. Any other root step that must act inside a `pi`-owned tree follows the same pattern.
- **Edit `config.toml` one table at a time.** Several tables share keys (`enabled` is in `[capture]`, `[daemon]`, `[web]` and every `[plugins.*]`), so never `sed` a key across the file: a file-wide `s/^enabled = .*/` once made `capture enable` switch on every plugin and `capture disable` switch off the daemon. Use `config-set <table> <key> <toml-value>` (`config_set`/`capture_config_set` in the shell tool; `plugins-ctl` imports it), which re-parses the result and refuses any edit that changes more than that one key.
- **Pip packages** go into the `pi` user's virtualenv at `/home/pi/.venv` (with system site-packages), not into the system Python. Keep `torch` pinned to a release that has a Python 3.11/arm64 wheel (no source builds: the image has no compiler). Only add packages a phase uses, and check they have an arm64 wheel.
- **Architecture:** the target is arm64 (e.g. the `aarch64-musl` AngryOxide build, arm64 pip wheels). Keep downloads arm64.
- **Base image bumps:** when changing `iso_url` in `builder/config.json`, update `iso_checksum` (SHA-256 of the `.img.xz`) at the same time, and check `target_image_size` still fits.
- **Nothing generated under `builder/extra/`:** every file there is copied into the image and is a rebuild prerequisite. Don't leave build or test artifacts (e.g. `__pycache__`) in it.
- **yamllint config:** formatting nits are disabled in `.yamllint`, but duplicate keys are errors.
- **Hostname isolation:** the Makefile wraps Packer in `unshare --uts` so the playbook's hostname change does not leak to the build host. Keep that wrapper.
